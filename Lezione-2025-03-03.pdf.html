Introduction

This course provides an introduction to the fundamental concepts of languages and compilers. We will explore the implementation of programming languages and the structure of a compiler, which is a crucial tool in the software development process. Understanding compilers allows us to bridge the gap between high-level programming languages, which are easy for humans to understand and use, and the low-level machine code that computers can directly execute.

This introductory lecture will cover the topics we will explore throughout the course, the implementation languages we will use, and some important organizational details. We will begin by outlining the key components of a compiler and then delve into the theoretical foundations of formal languages and grammars, which are essential for understanding how compilers work.

The main objectives of this lecture are:

  • To introduce the concept of compiler and its importance in computer science.

  • To outline the structure of a compiler and the role of each module.

  • To define formal languages and context-free grammars as tools for describing programming language syntax.

  • To discuss implementation languages and course logistics.

Key concepts covered in this lecture include:

  • Compiler structure (Lexical Analysis, Syntax Analysis, Semantic Analysis, etc.)

  • Intermediate representation

  • Formal languages, alphabets, strings, and languages

  • Context-free grammars, terminals, non-terminals, production rules

  • Concrete syntax trees (parse trees)

  • Backus-Naur Form (BNF)

Compiler Structure and Implementation

Implementation of a Programming Language

Implementing a programming language involves creating a system that can execute programs written in that language. A common approach is to use an intermediate machine and an emulator. This approach involves three key languages and two abstract machines.

  • Source Language: This is the programming language we want to implement. The goal is to design an abstract machine capable of executing instructions written in this language.

  • Target Language (or Object Language): This is the machine language of a host abstract machine, which is readily available. It is the language that our implementation will ultimately produce, enabling execution on the host machine.

  • Intermediate Language: This language serves as a strategic compromise between the source and target languages. It is designed to simplify the compilation process by offering a level of abstraction that is easier to translate from the source language and to the target language. The intermediate language acts as a bridge, streamlining the overall translation.

We also consider two abstract machines involved in the implementation, which may sometimes be the same physical machine:

  • Host Abstract Machine: This existing machine is responsible for executing the intermediate abstract machine emulator. It provides the environment in which the intermediate language programs are run.

  • Compiler Abstract Machine: This machine is responsible for executing the compiler itself. The compiler, running on this machine, performs the translation from the source language to the intermediate language.

Structure of a Compiler: Seven Modules

A compiler is typically structured into several phases or modules, each responsible for a specific task in the translation process. A common structure involves seven modules, often grouped into a Front End and a Back End, as depicted in 2.

  • Lexical Analyzer (Lexer/Scanner):

    • Function: The lexer is the initial phase, processing the source code as a stream of characters. It aggregates these characters into meaningful sequences called lexemes.

    • Output: For each identified lexeme, the lexer produces a token. A token represents the category of the lexeme, such as identifier, keyword, or operator. Tokens can also carry attributes, like the value of an identifier or a numeric constant.

  • Syntax Analyzer (Parser):

    • Function: The parser receives the stream of tokens from the lexical analyzer. It verifies if this sequence of tokens adheres to the grammatical rules of the programming language.

    • Output: If the token sequence is syntactically correct, the parser constructs an abstract syntax tree (AST). The AST is a hierarchical representation of the program’s structure. If syntax errors are found, the parser reports these errors, halting the compilation process or providing error messages.

  • Static Semantics Analyzer:

    • Function: This module performs checks on the AST to enforce static semantic rules of the language. This includes type checking, which ensures operations are type-consistent, and other compile-time semantic validations.

    • Output: The static semantics analyzer may augment the AST with type information or perform structural modifications to enforce semantic correctness, producing an enriched AST.

  • Intermediate Code Generator:

    • Function: This phase translates the semantically analyzed AST into an intermediate representation (IR).

    • Output: The IR is designed to be machine-independent, simplifying the subsequent translation to machine code. Three Address Code is a common form of IR. The intermediate language is a balance between being easy to generate from the AST and easy to translate into various target machine codes.

  • Machine Independent Code Optimizer:

    • Function: This module optimizes the intermediate code to enhance performance metrics such as execution speed and memory usage.

    • Scope: These optimizations are machine-independent, focusing on algorithmic and structural improvements in the IR.

  • Code Generator:

    • Function: The code generator takes the optimized intermediate code and converts it into the target machine code.

    • Output: This machine code is the compiler’s final product, ready for execution on the target machine.

  • Machine Dependent Code Optimizer:

    • Function: This module applies optimizations that are specific to the target machine’s architecture.

    • Scope: By leveraging machine-specific features, it further refines the generated code for optimal performance on a particular hardware platform.

  • Symbol Table:

    • Function: The symbol table is a crucial data structure used throughout all compilation phases. It stores detailed information about identifiers (variables, functions, etc.) found in the source code.

    • Contents: It maintains attributes such as type, scope, and memory location for each identifier, facilitating efficient information retrieval and management during compilation.

Remark. Remark 1.

Attention: It is essential to differentiate between two types of intermediate languages in the context of compilers:

  • Intermediate Language of the Compiler: This is an internal representation used within the compiler, between the front-end and back-end stages. It is a language designed for compiler’s internal operations.

  • Intermediate Language of Programming Language Implementation: This refers to the target language produced by the compiler. It is the "intermediate" language in the sense of the programming language implementation architecture, but from the compiler’s perspective, it is the final output or target language.

Confusing these two can lead to misunderstandings about the compilation process. The intermediate language discussed in the context of compiler phases is a construct to facilitate compilation, while the intermediate language in programming language implementation is a step in executing source code on a host machine.

Lexical Analysis in Detail

The lexical analysis module, also known as the lexer or scanner, is the first phase of compilation. Its primary role is to transform the raw input source code, which is essentially a stream of characters, into a structured stream of tokens. This process is crucial for simplifying the subsequent stages of compilation. The lexer operates by:

  • Aggregating Characters: It reads consecutive characters and groups them into lexemes, which are sequences of characters that together form a meaningful unit, like identifiers, keywords, operators, or constants.

  • Producing Tokens: For each recognized lexeme, the lexer generates a token. A token is a pair consisting of a token name and an optional attribute value. The token name represents the category of the lexeme (e.g., IDENTIFIER, NUMBER, OPERATOR), and the attribute value provides additional information, such as the actual string for an identifier or the numeric value for a number.

Example 2.

Consider the following line of source code:

pos = init + rate * 3.5

The lexical analyzer processes this line and outputs a sequence of tokens. Each token represents a lexeme identified in the input. For instance, the input line is broken down into tokens as follows:

  • pos is identified as an identifier and becomes a token, say, \(\langle id, \text{value} \rightarrow \text{pointer to symbol table entry for 'pos'} \rangle\). For simplicity, we denote it as \(\langle id_1 \rangle\).

  • = is recognized as the assignment operator, resulting in a token like \(\langle assign \rangle\).

  • init is another identifier, tokenized as \(\langle id, \text{value} \rightarrow \text{pointer to symbol table entry for 'init'} \rangle\), or simply \(\langle id_2 \rangle\).

  • + is the addition operator, tokenized as \(\langle add \rangle\).

  • rate is an identifier, tokenized as \(\langle id, \text{value} \rightarrow \text{pointer to symbol table entry for 'rate'} \rangle\), or \(\langle id_3 \rangle\).

  • * is the multiplication operator, tokenized as \(\langle mul \rangle\).

  • 3.5 is a number, tokenized as \(\langle num, \text{value} \rightarrow 3.5 \rangle\), or \(\langle num_4 \rangle\).

Thus, the token stream produced by the lexical analyzer for the input line is:

\(\langle id_1 \rangle\) \(\langle assign \rangle\) \(\langle id_2 \rangle\) \(\langle add \rangle\) \(\langle id_3 \rangle\) \(\langle mul \rangle\) \(\langle num_4 \rangle\)

Simultaneously, the symbol table is populated. For example, it would store entries for identifiers and potentially numbers:

  • Entry 1: name = pos

  • Entry 2: name = init

  • Entry 3: name = rate

  • Entry 4: value = 3.5

In simplified notation, we can represent these mappings as: 1 \(\rightarrow\) pos, 2 \(\rightarrow\) init, 3 \(\rightarrow\) rate, 4 \(\rightarrow\) 3.5.

Syntax Analysis in Detail

The syntax analysis module, or parser, is the second phase of compilation. It takes the token stream generated by the lexical analyzer and checks if the sequence of tokens forms a valid program according to the grammar of the programming language. The parser’s main functions are:

  • Grammar Validation: It determines if the input token stream conforms to the syntactic rules defined by the language’s grammar. This involves verifying the order and structure of tokens.

  • Abstract Syntax Tree (AST) Construction: If the token stream is syntactically correct, the parser constructs an abstract syntax tree (AST). The AST is a hierarchical tree structure that represents the syntactic structure of the program, discarding unnecessary details from the concrete syntax.

  • Error Reporting: If the token stream does not comply with the language’s grammar (i.e., syntax errors are detected), the parser reports these errors. Error reports typically include the type of error and the location in the source code where the error occurred.

Example 3.

Consider the token stream from the lexical analysis example:

\(\langle id_1 \rangle\) \(\langle assign \rangle\) \(\langle id_2 \rangle\) \(\langle add \rangle\) \(\langle id_3 \rangle\) \(\langle mul \rangle\) \(\langle num_4 \rangle\)

The syntax analyzer processes this token stream to validate its structure and build an AST. For the given token stream, assuming it is syntactically correct according to the language grammar, the parser would construct an AST. A possible AST for this expression is shown in 3. The root of the tree is an assignment operation (assign). The left child is the identifier pos (\(id_1\)), and the right child represents the expression init + rate * 3.5. This expression is further structured with addition (add) at the top, having init (\(id_2\)) as the left child and multiplication (mul) as the right child. The multiplication node has rate (\(id_3\)) and 3.5 (\(num_4\)) as its children.

Static Semantics Analysis in Detail

The static semantics analysis phase operates on the abstract syntax tree (AST) produced by the syntax analyzer. This phase is crucial for enforcing the semantic rules of the programming language that can be checked at compile time, before program execution. The key responsibilities of the static semantics analyzer include:

  • Semantic Constraint Checking: It verifies semantic rules that are not captured by the syntax, such as type compatibility, variable declarations, and scope rules. These are referred to as static semantics constraints.

  • AST Enrichment and Modification: Based on the semantic analysis, the AST may be enriched with additional information, such as type annotations, or modified to make later compilation phases easier. For instance, implicit type conversions might be made explicit in the AST.

Example 4.

Continuing with our example, consider the AST from syntax analysis for pos = init + rate * 3.5. The static semantics analyzer now checks for semantic correctness, including type checking. Suppose we have the following type information from declarations or default rules:

  • pos is of type float.

  • init is of type float.

  • rate is of type int.

  • 3.5 is a floating-point number (type float).

During static semantics analysis, the analyzer would perform type checking:

  1. Multiplication Operation: It examines the operation rate * 3.5. Since rate is int and 3.5 is float, and assuming the language rules allow mixed-type arithmetic, the result of this operation will typically be promoted to float.

  2. Addition Operation: Next, it checks init + (rate * 3.5). Here, init is float, and the result of rate * 3.5 is also float. Adding two floats results in a float, which is type-consistent.

  3. Assignment Operation: Finally, it verifies the assignment pos = (init + rate * 3.5). pos is declared as float, and the expression on the right-hand side is also of type float. This assignment is type-consistent.

If the language requires explicit type conversion in mixed-type operations, the static semantics analyzer might modify the AST to include an explicit conversion node. For example, it might insert a node to convert rate from int to float before the multiplication, as shown in 4. This ensures that all operations are performed on compatible types, possibly by inserting necessary type conversion operations.

Intermediate Code Generation in Detail

The intermediate code generation phase is responsible for translating the semantically-validated abstract syntax tree (AST) into an intermediate representation (IR). This IR is designed to be:

  • Machine-Independent: Unlike machine code, IR is not specific to any particular hardware architecture. This allows for portability and enables optimizations that are not tied to a specific machine.

  • Easier to Translate: IR is structured to be simpler to generate from the AST than machine code and also easier to translate into machine code for various target architectures. It serves as a bridge between the high-level AST and low-level machine code.

  • Suitable for Optimization: IR is designed to facilitate optimizations. Common intermediate representations are structured to allow for analyses and transformations that improve code performance.

A widely used form of intermediate representation is Three Address Code (TAC). In TAC, each instruction typically has at most three operands: two for input and one for output. It simplifies operations and makes the flow of data explicit.

Example 5.

Consider the semantically analyzed AST from the previous stage, possibly including explicit type conversions. The intermediate code generator translates this AST into Three Address Code. For our example AST, the intermediate code might look like this:

t0 = convert-int-to-float rate
t1 = t0 * 3.5
t2 = init + t1
pos = t2

In this TAC representation:

  • t0, t1, t2 are temporary variables created by the compiler to hold intermediate values.

  • convert-int-to-float is an explicit operation for type conversion, inserted based on the static semantics analysis.

  • Each line represents a simple operation, typically involving at most three addresses (operands and result).

This intermediate code is a linear sequence of instructions, which is easier to optimize and translate into target machine code in the subsequent phases of compilation. The use of temporary variables and explicit operations simplifies the representation and makes it suitable for further processing.

Intermediate and Target Code Optimization

The code optimization phase in a compiler aims to improve the intermediate or target code to enhance program performance. This improvement can be in terms of:

  • Faster Execution: Reducing the execution time of the compiled program.

  • Reduced Memory Usage: Minimizing the memory footprint of the program.

  • Lower Energy Consumption: Decreasing the energy consumed during program execution, which is increasingly important for mobile and embedded systems.

Code optimization is generally divided into two main categories based on the stage at which it is applied:

  • Intermediate Code Optimization (Machine-Independent):

    • Scope: This type of optimization is performed on the intermediate representation (IR), such as Three Address Code.

    • Machine Independence: It is machine-independent, meaning the optimizations applied are not specific to any particular target machine architecture. The goal is to improve the IR in ways that will generally benefit performance across different architectures.

    • Techniques: Common techniques include:

      • Constant Folding: Evaluating constant expressions at compile time.

      • Dead Code Elimination: Removing code that does not affect the program’s result.

      • Loop Optimization: Improving the efficiency of loops, such as loop unrolling or loop invariant code motion.

  • Target Code Optimization (Machine-Dependent):

    • Scope: This optimization is applied to the target machine code, which is specific to a particular architecture.

    • Machine Dependence: It leverages specific features and instructions of the target machine to further optimize the code.

    • Techniques: Examples include:

      • Register Allocation: Efficiently assigning variables to registers to minimize memory access.

      • Instruction Scheduling: Reordering instructions to maximize pipeline utilization and reduce stalls.

      • Machine-Specific Instruction Selection: Choosing the most efficient machine instructions for operations.

The optimization phase can be quite complex and may involve multiple passes of analysis and transformation over the code. The effectiveness of optimization can significantly impact the performance of the final executable program.

Formal Languages and Context-Free Grammars

Formal Languages: Basic Definitions

To formally define the syntax of programming languages, we use the concept of formal languages. Formal language theory provides a mathematical framework for describing the set of valid strings in a language, which is essential for compiler design.

Definition 6.

Alphabet (or Vocabulary): An alphabet \(T\) is a finite set of symbols. In the context of compilers, these symbols are often referred to as tokens, which are the basic building blocks recognized by the lexical analyzer.

Examples of alphabets include the set of ASCII characters, the set of Unicode characters, or, more specifically for compilers, a set of tokens like {IDENTIFIER, NUMBER, KEYWORD, OPERATOR}.

Definition 7.

String: A string (or word) is a finite sequence of symbols from an alphabet.

For instance, if our alphabet is the set of letters {a, b, c}, then "ab", "bacca", and "c" are strings over this alphabet. The source code of a program can be viewed as a long string over some alphabet.

Definition 8.

Language: A language \(L\) over an alphabet \(T\) is a set of strings over \(T\). A formal language over an alphabet \(T\) is formally defined as a subset of \(T^*\), where \(T^*\) (Kleene star of \(T\)) denotes the set of all possible finite sequences of elements from \(T\), including the empty string.

Thus, a language is simply a collection of strings. For example, if \(T= \{\text{0, 1}\}\), then one language over \(T\) could be the set of all binary strings that represent even numbers: \(L = \{\varepsilon, \text{"0"}, \text{"10"}, \text{"00"}, \text{"110"}, \text{"010"}, \ldots \}\). Another language could be the set of all valid programs in a specific programming language, like C or Java.

Definition 9.

Empty String: The empty string, denoted by \(\varepsilon\) (epsilon), is a special string that contains no symbols. It is the string of length zero.

The empty string is included in \(T^*\) for any alphabet \(T\). It is important in formal language theory for handling base cases and optional constructs in grammars.

The set of all syntactically correct programs in a programming language forms a formal language. This means that the syntax of a programming language can be precisely defined as a formal language.

Example 10.

For the C language, the set of all valid C programs is a formal language. An example of a string belonging to this language is:

{ int x = 3+y; void main() {if (x > 22) j += 3; } ,...}

This string, when tokenized and parsed, would be recognized as a valid (though incomplete) C program fragment by aC compiler.

Context-Free Grammars: Definition

Context-free grammars (CFGs) are a powerful and widely used formalism for describing the syntax of programming languages. They provide a set of rules that define how to generate all valid strings of a formal language, and they are expressive enough to capture the structure of most programming language constructs.

Definition 11.

A Context-Free Grammar (CFG) \(G\) is a 4-tuple \(G = (T, NT, \mathcal{S}, R)\), where:

  • \(T\) (Terminals): A finite set of terminal symbols. These are the basic, indivisible symbols of the language. In a compiler context, terminals are the tokens produced by the lexical analyzer. They are called "terminals" because they are the final symbols in the derivation process and do not get replaced further.

  • \(NT\) (Non-terminals): A finite set of non-terminal symbols, disjoint from \(T\). These symbols represent syntactic categories or constructs in the language. They are essentially placeholders for patterns of terminals and non-terminals and are used to define the structure of the language. Non-terminals are also called syntactic variables.

  • \(\mathcal{S}\) (Start Symbol): A special non-terminal symbol, \(\mathcal{S}\in NT\). It is the root symbol of the grammar and represents the most encompassing syntactic category, such as ‘program’ or ‘expression’. Derivation in a grammar always begins from the start symbol.

  • \(R\) (Rules or Productions): A finite set of production rules. Each rule is of the form \(A \rightarrow w\), where \(A \in NT\) is a non-terminal, and \(w \in (T\cup NT)^*\) is a sequence of terminals and non-terminals (possibly empty). A production rule specifies how a non-terminal can be replaced by a sequence of terminals and non-terminals.

In essence, a CFG provides a set of recursive rules to generate strings of a language. Starting from the start symbol, we repeatedly apply production rules, replacing non-terminals with their definitions until we obtain a string consisting only of terminal symbols.

Example 12.

Example Grammar \(G_{EXPR}\): Let’s define a grammar \(G_{EXPR}\) for simple arithmetic expressions involving addition and multiplication of numbers. \[G_{EXPR} = (\{\texttt{num}, \texttt{+}, \texttt{*}\}, \{E\}, E, R),\] where:

  • Terminals \(T= \{\texttt{num}, \texttt{+}, \texttt{*}\}\). Here, num represents any number, + represents the addition operator, and * represents the multiplication operator.

  • Non-terminals \(NT= \{E\}\). \(E\) is a non-terminal representing an ‘Expression’.

  • Start symbol \(\mathcal{S}= E\). We start derivations from the non-terminal \(E\).

  • Productions \(R\) are the set of rules: \[\begin{aligned} E &\rightarrow E + E \\ E &\rightarrow E * E \\ E &\rightarrow \texttt{num} \end{aligned}\]

These rules can be interpreted as:

  • Rule 1: An expression can be formed by combining two expressions with an addition operator in between.

  • Rule 2: An expression can be formed by combining two expressions with a multiplication operator in between.

  • Rule 3: An expression can be a number.

Using these rules, we can generate various arithmetic expressions, such as "num", "num + num", "num * num", "num + num * num", etc.

Backus-Naur Form (BNF)

Backus-Naur Form (BNF) is a metasyntax, i.e., a syntax for describing syntax, widely used for expressing context-free grammars. BNF provides a standardized, readable, and compact notation for grammar rules, making language specifications easier to understand and implement.

BNF Conventions:

  • Non-terminal Symbols: Non-terminals are enclosed in angle brackets: \(\langle NonTerminal \rangle\). This convention clearly distinguishes non-terminals from terminals.

  • Terminal Symbols: Terminals are usually enclosed in double quotes: "terminal". This helps to differentiate terminals, which are literal symbols, from non-terminals. Sometimes, if terminals are easily recognizable (e.g., keywords, operators), quotes might be omitted for brevity.

  • Production Rule Operator: The symbol \(::=\) is used instead of \(\rightarrow\) to denote production rules. It reads as "is defined as" or "can be replaced by".

  • Alternatives: Alternative productions for the same non-terminal are separated by the symbol \(|\). This allows for multiple ways a non-terminal can be expanded, all in a single rule.

Using BNF, the grammar \(G_{EXPR}\) can be written as:

<E> ::= <E> "+" <E> | <E> "*" <E> | "num"

This BNF representation is more concise and often easier to read than the set of rules notation. It clearly shows that an expression \(\langle E \rangle\) can be formed in three ways: by adding two expressions, by multiplying two expressions, or by being a number "num".

BNF, and its variants like Extended BNF (EBNF), are extensively used in language specifications, document formats (like XML), and communication protocols to formally define syntax rules. Parser generators often accept grammar specifications in BNF-like formats.

Strings Generated by a Grammar

A context-free grammar is used to generate strings of a language. The process of generation starts from the start symbol and applies production rules to replace non-terminals until only terminals remain. The sequence of terminals produced in this process is a string generated by the grammar.

Definition 15.

Given a concrete syntax tree for a non-terminal \(N\), the sequence of its leaf nodes, when read from left to right (and ignoring any leaf nodes labeled with the empty string \(\varepsilon\)), forms a string that is said to be generated from \(N\). This string is the yield of the parse tree.

Definition 17.

Two grammars \(G\) and \(G'\) are considered equivalent if they generate the same language, i.e., \(L(G) = L(G')\). It is important to note that equivalent grammars can have different structures and rules but still define the same set of valid strings.

Example 18.

For the grammar \(G_{EXPR}\), consider the string num * num + num. This string is in \(L(G_{EXPR})\) because we can construct a syntax tree for the start symbol \(E\) that generates this string, as shown in 6. The leaves of this tree, read from left to right, are "num", "*", "num", "+", "num", which form the string num * num + num.

Remark. Remark 19.

Important Disclaimer: It is crucial to distinguish between languages and grammars.

  • A language is a set of strings. It is a mathematical object that exists independently of any grammar.

  • A grammar is a set of rules that describes* or generates a language. It is a system of rules.*

Different grammars can generate the same language. For example, we can write multiple context-free grammars that all define the language of regular expressions. Furthermore, there are languages that cannot be generated by context-free grammars. These are called context-sensitive or even more complex languages. There are also languages that cannot be described by any grammar at all (non-recursively enumerable languages), although context-free grammars are sufficient for defining the syntax of most programming languages.

Implementation Languages for the Course

In this course, we will explore the practical aspects of compiler construction by implementing various compiler components. To facilitate this, we will utilize a selection of programming languages and tools that are well-suited for compiler development. The choice of these languages is based on their features and the availability of robust tools that simplify the development process. We will primarily use the following languages:

  • Haskell Language (with Alex and Happy):

    • Rationale: Haskell, a purely functional programming language, is exceptionally well-suited for compiler construction. Its strengths lie in its support for:

      • Algebraic Data Types: Haskell’s algebraic data types allow for concise and clear representation of complex data structures like Abstract Syntax Trees (ASTs) and intermediate representations.

      • Pattern Matching: Pattern matching simplifies the implementation of recursive algorithms and tree traversals, which are fundamental in compiler phases like semantic analysis and code generation.

      • Parsing Capabilities: Functional programming paradigms naturally align with parsing techniques, making Haskell an elegant choice for implementing parsers.

    • Tools: We will use:

      • Alex: A lexical analyzer generator for Haskell. Alex takes a specification of tokens in the form of regular expressions and generates Haskell code for a lexer.

      • Happy: A parser generator for Haskell, similar to Yacc or Bison. Happy takes a grammar specification and produces a Haskell parser.

  • C, C++, or Java Languages (with Flex/JFlex and Bison/CUP):

    • Rationale: C, C++, and Java are imperative and object-oriented languages that are also frequently used in compiler implementation. Their advantages include:

      • Performance: C and C++ offer high performance and low-level control, which can be important for efficiency in compiler construction. Java provides portability and a rich ecosystem.

      • Object-Oriented Features (C++, Java): Object-oriented programming can help manage the complexity of a compiler by allowing modular and structured design.

      • Widespread Use and Community Support: These languages are widely used, ensuring ample resources, libraries, and community support for development.

    • Tools: We will utilize:

      • Flex (or JFlex for Java): These are lexical analyzer generators. Flex is for C/C++, and JFlex is a Java version. They generate code for scanners based on regular expression specifications.

      • Bison (or CUP for Java): These are parser generators. Bison is used with C/C++, and CUP (Construction of Useful Parsers) is for Java. They take grammar specifications and generate parser code, typically using LALR parsing techniques.

The specific choice of implementation language for assignments and projects within this course might vary depending on the task requirements and pedagogical goals. Both Haskell and C/C++/Java, along with their respective toolchains, provide excellent platforms for learning and practicing compiler construction principles.

# Compiler Structure and Implementation

## Implementation of a Programming Language

Implementing a programming language involves creating a system that can
execute programs written in that language. A common approach is to use
an **intermediate machine** and an **emulator**. This approach involves
three key languages and two abstract machines.

-   **Source Language:** This is the programming language we want to
    implement. The goal is to design an abstract machine capable of
    executing instructions written in this language.

-   **Target Language (or Object Language):** This is the machine
    language of a host abstract machine, which is readily available. It
    is the language that our implementation will ultimately produce,
    enabling execution on the host machine.

-   **Intermediate Language:** This language serves as a strategic
    compromise between the source and target languages. It is designed
    to simplify the compilation process by offering a level of
    abstraction that is easier to translate from the source language and
    to the target language. The intermediate language acts as a bridge,
    streamlining the overall translation.

We also consider two abstract machines involved in the implementation,
which may sometimes be the same physical machine:

-   **Host Abstract Machine:** This existing machine is responsible for
    executing the **intermediate abstract machine emulator**. It
    provides the environment in which the intermediate language programs
    are run.

-   **Compiler Abstract Machine:** This machine is responsible for
    executing the **compiler** itself. The compiler, running on this
    machine, performs the translation from the source language to the
    intermediate language.

intermediate code is then executed by an Intermediate Machine Emulator
on a Host Abstract Machine to produce the program's

## Structure of a Compiler: Seven Modules

A compiler is typically structured into several phases or modules, each
responsible for a specific task in the translation process. A common
structure involves seven modules, often grouped into a **Front End** and
a **Back End**, as depicted in
[2](#fig:compiler_structure){reference-type="ref+label"
reference="fig:compiler_structure"}.

-   **Lexical Analyzer (Lexer/Scanner):**

    -   **Function:** The lexer is the initial phase, processing the
        source code as a stream of characters. It aggregates these
        characters into meaningful sequences called **lexemes**.

    -   **Output:** For each identified lexeme, the lexer produces a
        **token**. A token represents the category of the lexeme, such
        as identifier, keyword, or operator. Tokens can also carry
        attributes, like the value of an identifier or a numeric
        constant.

-   **Syntax Analyzer (Parser):**

    -   **Function:** The parser receives the stream of tokens from the
        lexical analyzer. It verifies if this sequence of tokens adheres
        to the grammatical rules of the programming language.

    -   **Output:** If the token sequence is syntactically correct, the
        parser constructs an **abstract syntax tree (AST)**. The AST is
        a hierarchical representation of the program's structure. If
        syntax errors are found, the parser reports these errors,
        halting the compilation process or providing error messages.

-   **Static Semantics Analyzer:**

    -   **Function:** This module performs checks on the AST to enforce
        static semantic rules of the language. This includes **type
        checking**, which ensures operations are type-consistent, and
        other compile-time semantic validations.

    -   **Output:** The static semantics analyzer may augment the AST
        with type information or perform structural modifications to
        enforce semantic correctness, producing an enriched AST.

-   **Intermediate Code Generator:**

    -   **Function:** This phase translates the semantically analyzed
        AST into an **intermediate representation (IR)**.

    -   **Output:** The IR is designed to be machine-independent,
        simplifying the subsequent translation to machine code. **Three
        Address Code** is a common form of IR. The intermediate language
        is a balance between being easy to generate from the AST and
        easy to translate into various target machine codes.

-   **Machine Independent Code Optimizer:**

    -   **Function:** This module optimizes the intermediate code to
        enhance performance metrics such as execution speed and memory
        usage.

    -   **Scope:** These optimizations are machine-independent, focusing
        on algorithmic and structural improvements in the IR.

-   **Code Generator:**

    -   **Function:** The code generator takes the optimized
        intermediate code and converts it into the **target machine
        code**.

    -   **Output:** This machine code is the compiler's final product,
        ready for execution on the target machine.

-   **Machine Dependent Code Optimizer:**

    -   **Function:** This module applies optimizations that are
        specific to the target machine's architecture.

    -   **Scope:** By leveraging machine-specific features, it further
        refines the generated code for optimal performance on a
        particular hardware platform.

-   **Symbol Table:**

    -   **Function:** The symbol table is a crucial data structure used
        throughout all compilation phases. It stores detailed
        information about identifiers (variables, functions, etc.) found
        in the source code.

    -   **Contents:** It maintains attributes such as type, scope, and
        memory location for each identifier, facilitating efficient
        information retrieval and management during compilation.

the seven compiler modules. The Lexical Analyzer takes source code and

Machine Independent and Dependent Code Optimizers enhance the

:::: remark
**Remark 1**.

::: tcolorbox
***Attention:** It is essential to differentiate between two types of
intermediate languages in the context of compilers:*

-   ***Intermediate Language of the Compiler:** This is an internal
    representation used within the compiler, between the front-end and
    back-end stages. It is a language designed for compiler's internal
    operations.*

-   ***Intermediate Language of Programming Language Implementation:**
    This refers to the target language produced by the compiler. It is
    the \"intermediate\" language in the sense of the programming
    language implementation architecture, but from the compiler's
    perspective, it is the final output or target language.*

*Confusing these two can lead to misunderstandings about the compilation
process. The intermediate language discussed in the context of compiler
phases is a construct to facilitate compilation, while the intermediate
language in programming language implementation is a step in executing
source code on a host machine.*
:::
::::

## Lexical Analysis in Detail

The **lexical analysis** module, also known as the lexer or scanner, is
the first phase of compilation. Its primary role is to transform the raw
input source code, which is essentially a stream of characters, into a
structured stream of tokens. This process is crucial for simplifying the
subsequent stages of compilation. The lexer operates by:

-   **Aggregating Characters:** It reads consecutive characters and
    groups them into **lexemes**, which are sequences of characters that
    together form a meaningful unit, like identifiers, keywords,
    operators, or constants.

-   **Producing Tokens:** For each recognized lexeme, the lexer
    generates a **token**. A token is a pair consisting of a *token
    name* and an optional *attribute value*. The token name represents
    the category of the lexeme (e.g., `IDENTIFIER`, `NUMBER`,
    `OPERATOR`), and the attribute value provides additional
    information, such as the actual string for an identifier or the
    numeric value for a number.

:::: example
**Example 2**.

::: tcolorbox
*Consider the following line of source code:*

``` {.objectivec language="C" basicstyle="\\ttfamily\\footnotesize"}
pos = init + rate * 3.5
```

*The lexical analyzer processes this line and outputs a sequence of
tokens. Each token represents a lexeme identified in the input. For
instance, the input line is broken down into tokens as follows:*

-   *`pos` is identified as an identifier and becomes a token, say,
    $\langle id, \text{value} \rightarrow \text{pointer to symbol table entry for 'pos'} \rangle$.
    For simplicity, we denote it as $\langle id_1 \rangle$.*

-   *`=` is recognized as the assignment operator, resulting in a token
    like $\langle assign \rangle$.*

-   *`init` is another identifier, tokenized as
    $\langle id, \text{value} \rightarrow \text{pointer to symbol table entry for 'init'} \rangle$,
    or simply $\langle id_2 \rangle$.*

-   *`+` is the addition operator, tokenized as $\langle add \rangle$.*

-   *`rate` is an identifier, tokenized as
    $\langle id, \text{value} \rightarrow \text{pointer to symbol table entry for 'rate'} \rangle$,
    or $\langle id_3 \rangle$.*

-   *`*` is the multiplication operator, tokenized as
    $\langle mul \rangle$.*

-   *`3.5` is a number, tokenized as
    $\langle num, \text{value} \rightarrow 3.5 \rangle$, or
    $\langle num_4 \rangle$.*

*Thus, the token stream produced by the lexical analyzer for the input
line is:*

*$\langle id_1 \rangle$ $\langle assign \rangle$ $\langle id_2 \rangle$
$\langle add \rangle$ $\langle id_3 \rangle$ $\langle mul \rangle$
$\langle num_4 \rangle$*

*Simultaneously, the symbol table is populated. For example, it would
store entries for identifiers and potentially numbers:*

-   *Entry 1: `name = pos`*

-   *Entry 2: `name = init`*

-   *Entry 3: `name = rate`*

-   *Entry 4: `value = 3.5`*

*In simplified notation, we can represent these mappings as: 1
$\rightarrow$ `pos`, 2 $\rightarrow$ `init`, 3 $\rightarrow$ `rate`, 4
$\rightarrow$ `3.5`.*
:::
::::

## Syntax Analysis in Detail

The **syntax analysis** module, or parser, is the second phase of
compilation. It takes the token stream generated by the lexical analyzer
and checks if the sequence of tokens forms a valid program according to
the grammar of the programming language. The parser's main functions
are:

-   **Grammar Validation:** It determines if the input token stream
    conforms to the syntactic rules defined by the language's grammar.
    This involves verifying the order and structure of tokens.

-   **Abstract Syntax Tree (AST) Construction:** If the token stream is
    syntactically correct, the parser constructs an **abstract syntax
    tree (AST)**. The AST is a hierarchical tree structure that
    represents the syntactic structure of the program, discarding
    unnecessary details from the concrete syntax.

-   **Error Reporting:** If the token stream does not comply with the
    language's grammar (i.e., syntax errors are detected), the parser
    reports these errors. Error reports typically include the type of
    error and the location in the source code where the error occurred.

:::: example
**Example 3**.

::: tcolorbox
*Consider the token stream from the lexical analysis example:*

*$\langle id_1 \rangle$ $\langle assign \rangle$ $\langle id_2 \rangle$
$\langle add \rangle$ $\langle id_3 \rangle$ $\langle mul \rangle$
$\langle num_4 \rangle$*

*The syntax analyzer processes this token stream to validate its
structure and build an AST. For the given token stream, assuming it is
syntactically correct according to the language grammar, the parser
would construct an AST. A possible AST for this expression is shown in
[3](#fig:ast_example){reference-type="ref+label"
reference="fig:ast_example"}. The root of the tree is an assignment
operation (`assign`). The left child is the identifier `pos` ($id_1$),
and the right child represents the expression `init + rate * 3.5`. This
expression is further structured with addition (`add`) at the top,
having `init` ($id_2$) as the left child and multiplication (`mul`) as
the right child. The multiplication node has `rate` ($id_3$) and `3.5`
($num_4$) as its children.*

![*Abstract Syntax Tree for `pos = init + rate * 3.5`. The root node
represents the assignment operation. The `add` node represents the
addition, and the `mul` node represents the multiplication, reflecting

## Static Semantics Analysis in Detail

The **static semantics analysis** phase operates on the abstract syntax
tree (AST) produced by the syntax analyzer. This phase is crucial for
enforcing the semantic rules of the programming language that can be
checked at compile time, before program execution. The key
responsibilities of the static semantics analyzer include:

-   **Semantic Constraint Checking:** It verifies semantic rules that
    are not captured by the syntax, such as type compatibility, variable
    declarations, and scope rules. These are referred to as **static
    semantics constraints**.

-   **AST Enrichment and Modification:** Based on the semantic analysis,
    the AST may be enriched with additional information, such as type
    annotations, or modified to make later compilation phases easier.
    For instance, implicit type conversions might be made explicit in
    the AST.

:::: example
**Example 4**.

::: tcolorbox
*Continuing with our example, consider the AST from syntax analysis for
`pos = init + rate * 3.5`. The static semantics analyzer now checks for
semantic correctness, including type checking. Suppose we have the
following type information from declarations or default rules:*

-   *`pos` is of type `float`.*

-   *`init` is of type `float`.*

-   *`rate` is of type `int`.*

-   *`3.5` is a floating-point number (type `float`).*

*During static semantics analysis, the analyzer would perform type
checking:*

1.  ***Multiplication Operation:** It examines the operation
    `rate * 3.5`. Since `rate` is `int` and `3.5` is `float`, and
    assuming the language rules allow mixed-type arithmetic, the result
    of this operation will typically be promoted to `float`.*

2.  ***Addition Operation:** Next, it checks `init + (rate * 3.5)`.
    Here, `init` is `float`, and the result of `rate * 3.5` is also
    `float`. Adding two floats results in a `float`, which is
    type-consistent.*

3.  ***Assignment Operation:** Finally, it verifies the assignment
    `pos = (init + rate * 3.5)`. `pos` is declared as `float`, and the
    expression on the right-hand side is also of type `float`. This
    assignment is type-consistent.*

*If the language requires explicit type conversion in mixed-type
operations, the static semantics analyzer might modify the AST to
include an explicit conversion node. For example, it might insert a node
to convert `rate` from `int` to `float` before the multiplication, as
shown in [4](#fig:ast_semantic_example){reference-type="ref+label"
reference="fig:ast_semantic_example"}. This ensures that all operations
are performed on compatible types, possibly by inserting necessary type
conversion operations.*

![*Abstract Syntax Tree with Static Semantics Information. The AST is
augmented with type information (e.g., `float`, `int`) attached to the
nodes. An explicit type conversion node `(int to float)` is inserted to
handle the mixed-type multiplication, making the type conversion
explicit in the AST.*](placeholder4.png){#fig:ast_semantic_example

## Intermediate Code Generation in Detail

The **intermediate code generation** phase is responsible for
translating the semantically-validated abstract syntax tree (AST) into
an **intermediate representation (IR)**. This IR is designed to be:

-   **Machine-Independent:** Unlike machine code, IR is not specific to
    any particular hardware architecture. This allows for portability
    and enables optimizations that are not tied to a specific machine.

-   **Easier to Translate:** IR is structured to be simpler to generate
    from the AST than machine code and also easier to translate into
    machine code for various target architectures. It serves as a bridge
    between the high-level AST and low-level machine code.

-   **Suitable for Optimization:** IR is designed to facilitate
    optimizations. Common intermediate representations are structured to
    allow for analyses and transformations that improve code
    performance.

A widely used form of intermediate representation is **Three Address
Code (TAC)**. In TAC, each instruction typically has at most three
operands: two for input and one for output. It simplifies operations and
makes the flow of data explicit.

:::: example
**Example 5**.

::: tcolorbox
*Consider the semantically analyzed AST from the previous stage,
possibly including explicit type conversions. The intermediate code
generator translates this AST into Three Address Code. For our example
AST, the intermediate code might look like this:*

``` {#lst:tac_example .pseudocode language="pseudocode" basicstyle="\\ttfamily\\footnotesize" caption="Three Address Code for 'pos = init + rate * 3.5'" label="lst:tac_example"}
t0 = convert-int-to-float rate
t1 = t0 * 3.5
t2 = init + t1
pos = t2
```

*In this TAC representation:*

-   *`t0`, `t1`, `t2` are temporary variables created by the compiler to
    hold intermediate values.*

-   *`convert-int-to-float` is an explicit operation for type
    conversion, inserted based on the static semantics analysis.*

-   *Each line represents a simple operation, typically involving at
    most three addresses (operands and result).*

*This intermediate code is a linear sequence of instructions, which is
easier to optimize and translate into target machine code in the
subsequent phases of compilation. The use of temporary variables and
explicit operations simplifies the representation and makes it suitable
for further processing.*
:::
::::

## Intermediate and Target Code Optimization

The **code optimization** phase in a compiler aims to improve the
intermediate or target code to enhance program performance. This
improvement can be in terms of:

-   **Faster Execution:** Reducing the execution time of the compiled
    program.

-   **Reduced Memory Usage:** Minimizing the memory footprint of the
    program.

-   **Lower Energy Consumption:** Decreasing the energy consumed during
    program execution, which is increasingly important for mobile and
    embedded systems.

Code optimization is generally divided into two main categories based on
the stage at which it is applied:

-   **Intermediate Code Optimization (Machine-Independent):**

    -   **Scope:** This type of optimization is performed on the
        intermediate representation (IR), such as Three Address Code.

    -   **Machine Independence:** It is machine-independent, meaning the
        optimizations applied are not specific to any particular target
        machine architecture. The goal is to improve the IR in ways that
        will generally benefit performance across different
        architectures.

    -   **Techniques:** Common techniques include:

        -   **Constant Folding:** Evaluating constant expressions at
            compile time.

        -   **Dead Code Elimination:** Removing code that does not
            affect the program's result.

        -   **Loop Optimization:** Improving the efficiency of loops,
            such as loop unrolling or loop invariant code motion.

-   **Target Code Optimization (Machine-Dependent):**

    -   **Scope:** This optimization is applied to the target machine
        code, which is specific to a particular architecture.

    -   **Machine Dependence:** It leverages specific features and
        instructions of the target machine to further optimize the code.

    -   **Techniques:** Examples include:

        -   **Register Allocation:** Efficiently assigning variables to
            registers to minimize memory access.

        -   **Instruction Scheduling:** Reordering instructions to
            maximize pipeline utilization and reduce stalls.

        -   **Machine-Specific Instruction Selection:** Choosing the
            most efficient machine instructions for operations.

The optimization phase can be quite complex and may involve multiple
passes of analysis and transformation over the code. The effectiveness
of optimization can significantly impact the performance of the final
executable program.

# Formal Languages and Context-Free Grammars

## Formal Languages: Basic Definitions

To formally define the syntax of programming languages, we use the
concept of **formal languages**. Formal language theory provides a
mathematical framework for describing the set of valid strings in a
language, which is essential for compiler design.

:::: definition
**Definition 6**.

::: tcolorbox
***Alphabet (or Vocabulary)**: An **alphabet** $T$ is a finite set of
symbols. In the context of compilers, these symbols are often referred
to as **tokens**, which are the basic building blocks recognized by the
lexical analyzer.*
:::
::::

Examples of alphabets include the set of ASCII characters, the set of
Unicode characters, or, more specifically for compilers, a set of tokens
like {IDENTIFIER, NUMBER, KEYWORD, OPERATOR}.

:::: definition
**Definition 7**.

::: tcolorbox
***String**: A **string** (or word) is a finite sequence of symbols from
an alphabet.*
:::
::::

For instance, if our alphabet is the set of letters {a, b, c}, then
\"ab\", \"bacca\", and \"c\" are strings over this alphabet. The source
code of a program can be viewed as a long string over some alphabet.

:::: definition
**Definition 8**.

::: tcolorbox
***Language**: A **language** $L$ over an alphabet $T$ is a set of
strings over $T$. A **formal language** over an alphabet $T$ is formally
defined as a subset of $T^*$, where $T^*$ (Kleene star of $T$) denotes
the set of all possible finite sequences of elements from $T$, including
the empty string.*
:::
::::

Thus, a language is simply a collection of strings. For example, if
$T= \{\text{0, 1}\}$, then one language over $T$ could be the set of all
binary strings that represent even numbers:
$L = \{\varepsilon, \text{"0"}, \text{"10"}, \text{"00"}, \text{"110"}, \text{"010"}, \ldots \}$.
Another language could be the set of all valid programs in a specific
programming language, like C or Java.

:::: definition
**Definition 9**.

::: tcolorbox
***Empty String**: The **empty string**, denoted by $\varepsilon$
(epsilon), is a special string that contains no symbols. It is the
string of length zero.*
:::
::::

The empty string is included in $T^*$ for any alphabet $T$. It is
important in formal language theory for handling base cases and optional
constructs in grammars.

The set of all syntactically correct programs in a programming language
forms a formal language. This means that the syntax of a programming
language can be precisely defined as a formal language.

:::: example
**Example 10**.

::: tcolorbox
*For the C language, the set of all valid C programs is a formal
language. An example of a string belonging to this language is:*

``` {.objectivec language="C" basicstyle="\\ttfamily\\footnotesize"}
{ int x = 3+y; void main() {if (x > 22) j += 3; } ,...}
```

*This string, when tokenized and parsed, would be recognized as a valid
(though incomplete) C program fragment by aC compiler.*
:::
::::

## Context-Free Grammars: Definition

**Context-free grammars (CFGs)** are a powerful and widely used
formalism for describing the syntax of programming languages. They
provide a set of rules that define how to generate all valid strings of
a formal language, and they are expressive enough to capture the
structure of most programming language constructs.

:::: definition
**Definition 11**.

::: tcolorbox
*A **Context-Free Grammar (CFG)** $G$ is a 4-tuple
$G = (T, NT, \mathcal{S}, R)$, where:*

-   *$T$ (Terminals): A finite set of terminal symbols. These are the
    basic, indivisible symbols of the language. In a compiler context,
    terminals are the **tokens** produced by the lexical analyzer. They
    are called \"terminals\" because they are the final symbols in the
    derivation process and do not get replaced further.*

-   *$NT$ (Non-terminals): A finite set of non-terminal symbols,
    disjoint from $T$. These symbols represent syntactic categories or
    constructs in the language. They are essentially placeholders for
    patterns of terminals and non-terminals and are used to define the
    structure of the language. Non-terminals are also called **syntactic
    variables**.*

-   *$\mathcal{S}$ (Start Symbol): A special non-terminal symbol,
    $\mathcal{S}\in NT$. It is the root symbol of the grammar and
    represents the most encompassing syntactic category, such as
    'program' or 'expression'. Derivation in a grammar always begins
    from the start symbol.*

-   *$R$ (Rules or Productions): A finite set of production rules. Each
    rule is of the form $A \rightarrow w$, where $A \in NT$ is a
    non-terminal, and $w \in (T\cup NT)^*$ is a sequence of terminals
    and non-terminals (possibly empty). A production rule specifies how
    a non-terminal can be replaced by a sequence of terminals and
    non-terminals.*
:::
::::

In essence, a CFG provides a set of recursive rules to generate strings
of a language. Starting from the start symbol, we repeatedly apply
production rules, replacing non-terminals with their definitions until
we obtain a string consisting only of terminal symbols.

:::: example
**Example 12**.

::: tcolorbox
***Example Grammar $G_{EXPR}$:** Let's define a grammar $G_{EXPR}$ for
simple arithmetic expressions involving addition and multiplication of
numbers.
$$G_{EXPR} = (\{\texttt{num}, \texttt{+}, \texttt{*}\}, \{E\}, E, R),$$
where:*

-   *Terminals $T= \{\texttt{num}, \texttt{+}, \texttt{*}\}$. Here,
    `num` represents any number, `+` represents the addition operator,
    and `*` represents the multiplication operator.*

-   *Non-terminals $NT= \{E\}$. $E$ is a non-terminal representing an
    'Expression'.*

-   *Start symbol $\mathcal{S}= E$. We start derivations from the
    non-terminal $E$.*

-   *Productions $R$ are the set of rules:
    $$\begin{aligned}        E &\rightarrow E + E \\        E &\rightarrow E * E \\        E &\rightarrow \texttt{num}    \end{aligned}$$*

*These rules can be interpreted as:*

-   *Rule 1: An expression can be formed by combining two expressions
    with an addition operator in between.*

-   *Rule 2: An expression can be formed by combining two expressions
    with a multiplication operator in between.*

-   *Rule 3: An expression can be a number.*

*Using these rules, we can generate various arithmetic expressions, such
as \"num\", \"num + num\", \"num \* num\", \"num + num \* num\", etc.*

## Backus-Naur Form (BNF)

**Backus-Naur Form (BNF)** is a metasyntax, i.e., a syntax for
describing syntax, widely used for expressing context-free grammars. BNF
provides a standardized, readable, and compact notation for grammar
rules, making language specifications easier to understand and
implement.

**BNF Conventions:**

-   **Non-terminal Symbols:** Non-terminals are enclosed in angle
    brackets: $\langle NonTerminal \rangle$. This convention clearly
    distinguishes non-terminals from terminals.

-   **Terminal Symbols:** Terminals are usually enclosed in double
    quotes: `"terminal"`. This helps to differentiate terminals, which
    are literal symbols, from non-terminals. Sometimes, if terminals are
    easily recognizable (e.g., keywords, operators), quotes might be
    omitted for brevity.

-   **Production Rule Operator:** The symbol $::=$ is used instead of
    $\rightarrow$ to denote production rules. It reads as \"is defined
    as\" or \"can be replaced by\".

-   **Alternatives:** Alternative productions for the same non-terminal
    are separated by the symbol $|$. This allows for multiple ways a
    non-terminal can be expanded, all in a single rule.

Using BNF, the grammar $G_{EXPR}$ can be written as:

    <E> ::= <E> "+" <E> | <E> "*" <E> | "num"

This BNF representation is more concise and often easier to read than
the set of rules notation. It clearly shows that an expression
$\langle E \rangle$ can be formed in three ways: by adding two
expressions, by multiplying two expressions, or by being a number
\"num\".

BNF, and its variants like Extended BNF (EBNF), are extensively used in
language specifications, document formats (like XML), and communication
protocols to formally define syntax rules. Parser generators often
accept grammar specifications in BNF-like formats.

## Strings Generated by a Grammar

A context-free grammar is used to generate strings of a language. The
process of generation starts from the start symbol and applies
production rules to replace non-terminals until only terminals remain.
The sequence of terminals produced in this process is a string generated
by the grammar.

:::: definition
**Definition 15**.

::: tcolorbox
*Given a concrete syntax tree for a non-terminal $N$, the sequence of
its leaf nodes, when read from left to right (and ignoring any leaf
nodes labeled with the empty string $\varepsilon$), forms a string that
is said to be **generated** from $N$. This string is the yield of the
parse tree.*

:::: remark
**Remark 19**.

::: tcolorbox
***Important Disclaimer:** It is crucial to distinguish between
**languages** and **grammars**.*

-   *A **language** is a set of strings. It is a mathematical object
    that exists independently of any grammar.*

-   *A **grammar** is a set of rules that *describes* or *generates* a
    language. It is a system of rules.*

*Different grammars can generate the same language. For example, we can
write multiple context-free grammars that all define the language of
regular expressions. Furthermore, there are languages that cannot be
generated by context-free grammars. These are called context-sensitive
or even more complex languages. There are also languages that cannot be
described by any grammar at all (non-recursively enumerable languages),
although context-free grammars are sufficient for defining the syntax of
most programming languages.*

# Implementation Languages for the Course

In this course, we will explore the practical aspects of compiler
construction by implementing various compiler components. To facilitate
this, we will utilize a selection of programming languages and tools
that are well-suited for compiler development. The choice of these
languages is based on their features and the availability of robust
tools that simplify the development process. We will primarily use the
following languages:

-   **Haskell Language (with Alex and Happy):**

    -   **Rationale:** Haskell, a purely functional programming
        language, is exceptionally well-suited for compiler
        construction. Its strengths lie in its support for:

        -   **Algebraic Data Types:** Haskell's algebraic data types
            allow for concise and clear representation of complex data
            structures like Abstract Syntax Trees (ASTs) and
            intermediate representations.

        -   **Pattern Matching:** Pattern matching simplifies the
            implementation of recursive algorithms and tree traversals,
            which are fundamental in compiler phases like semantic
            analysis and code generation.

        -   **Parsing Capabilities:** Functional programming paradigms
            naturally align with parsing techniques, making Haskell an
            elegant choice for implementing parsers.

    -   **Tools:** We will use:

        -   **Alex:** A lexical analyzer generator for Haskell. Alex
            takes a specification of tokens in the form of regular
            expressions and generates Haskell code for a lexer.

        -   **Happy:** A parser generator for Haskell, similar to Yacc
            or Bison. Happy takes a grammar specification and produces a
            Haskell parser.

-   **C, C++, or Java Languages (with Flex/JFlex and Bison/CUP):**

    -   **Rationale:** C, C++, and Java are imperative and
        object-oriented languages that are also frequently used in
        compiler implementation. Their advantages include:

        -   **Performance:** C and C++ offer high performance and
            low-level control, which can be important for efficiency in
            compiler construction. Java provides portability and a rich
            ecosystem.

        -   **Object-Oriented Features (C++, Java):** Object-oriented
            programming can help manage the complexity of a compiler by
            allowing modular and structured design.

        -   **Widespread Use and Community Support:** These languages
            are widely used, ensuring ample resources, libraries, and
            community support for development.

    -   **Tools:** We will utilize:

        -   **Flex (or JFlex for Java):** These are lexical analyzer
            generators. Flex is for C/C++, and JFlex is a Java version.
            They generate code for scanners based on regular expression
            specifications.

        -   **Bison (or CUP for Java):** These are parser generators.
            Bison is used with C/C++, and CUP (Construction of Useful
            Parsers) is for Java. They take grammar specifications and
            generate parser code, typically using LALR parsing
            techniques.

The specific choice of implementation language for assignments and
projects within this course might vary depending on the task
requirements and pedagogical goals. Both Haskell and C/C++/Java, along
with their respective toolchains, provide excellent platforms for
learning and practicing compiler construction principles.
